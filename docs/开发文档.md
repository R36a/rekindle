## 1. 项目定位

### 1.1 一句话

> 一个本地优先的个人人脉管理工具——无服务器、无埋点，用你自己的 LLM API key，用一句话记人，靠提醒维持联系。

### 1.2 目标用户

| 顺序 | 用户 | 说明 |
|---|---|---|
| 1 | **作者本人**（dogfooding） | 唯一的功能裁决者；任何功能必须自己每天在用 |
| 2 | 在意隐私、手上有 LLM API key 的开发者 | 第二用户，用来检验"没有作者在场时能否跑起来" |

**明确不服务的用户**：需要团队协作、需要手机端同步、需要"开箱即用零配置"的普通消费者。
（这不是鄙视，而是 v1 的能力边界；服务他们的成本会让 v1 做不完。）

### 1.3 不是什么

- 不是 AI 日记，不是 AI 陪聊，不是通用笔记工具；
- 不是 SaaS：没有账号体系、没有云端、没有自有服务端；
- 不是「社交 CRM」：不做销售漏斗、不做批量群发、不做联系人自动抓取。

### 1.4 v1 成功长什么样（先定验收，再写代码）

1. 连续自用 **14 天**，累计 **≥50 条**真实记录（不是测试数据）；
2. 从「想到某人」到「确认入库」的 **P50 ≤ 3 秒**（用真实热键计时，不是估算）；
3. 抽取字段级准确率 **≥75%**，且该数字可由仓库内脚本复现（见设计细节 6）；
4. 关掉程序 48 小时再打开，**逾期提醒恰好出现一次**（不丢、不重复）；
5. 导出的 JSON 能在**另一个空库**里完整恢复（往返一致性测试）。

## 2. 设计原则与裁决

### 2.1 裁决优先级（冲突时从 P0 往 P4 判，高者胜）

| 级别 | 原则 | 判定方式（可反驳的形式） |
|---|---|---|
| **P0** | **不丢数据、不做假承诺** | 数据丢失 = 阻塞发布；README 里出现无法被用户自行验证的承诺 = 删除该承诺 |
| **P1** | **主路径 ≤3 秒** | 用计时器实测；新功能若让 P50 超过 3s，砍功能而不是砍速度 |
| **P2** | **容错优先于全自动** | 任何"用户不用看就写入"的设计一律否决；LLM 结果必须经过确认步骤 |
| **P3** | **无自有服务端，且可审计** | 出站目标只有"用户配置的端点"；每次请求可查看、可回放、可在测试中断言 |
| **P4** | **好用** | 前四条都满足时，选用户更省事的那条 |

> P3 低于 P1/P2 是刻意的：**"更隐私"不构成让主路径变慢或让数据更容易丢的理由**。
> 但 P3 是硬边界（不可关闭的能力），不是可调参数。

### 2.2 原则表（v0.2 口径）

| 原则 | 含义 | 冲突时 |
|---|---|---|
| 无自有服务端 | 本项目不运营任何服务器；出站仅限用户配置的 LLM 端点 | 任何需要自建服务端的便利功能，砍掉 |
| 可离线 | 规则抽取在本地完成，零网络 | 离线可用的功能优先于"更聪明的在线功能" |
| 入口 < 3 秒 | 想记 → 记下来确认，P50 ≤ 3s | 新功能让主路径变长则砍掉 |
| 可验证 | 主张必须能被用户审计（日志、白名单、导出） | 不能验证的承诺不写进 README |
| 容错优先 | 预填 + 确认 > 全自动 | 不做"用户完全不用看"的自动写入 |

## 3. 产品边界

### 3.1 v1 做（含验收口径）

| 功能 | 说明 | 验收口径 |
|---|---|---|
| **一句话记录** | 全局热键唤起输入框，粘贴/口述式一句话 | 唤起 → 可输入 ≤0.5s |
| **规则抽取（离线）** | 正则 + 中文日期解析 + 姓名/公司/承诺启发式，零网络 | 断网可用；20 条固定用例全绿 |
| **LLM 结构化抽取** | OpenAI 兼容接口，输出 **Pydantic 严格 schema** | 校验失败自动修复重试 1 次；仍失败则降级到规则抽取并标记 |
| **预填 + 确认** | 抽取结果填进表单，用户改 1~2 个字段后确认 | 未点确认 → 数据库里只有 `capture`，无 `interaction` |
| **实体消歧** | 同名/别名/拼音候选，用户选择 | 同一人不会因为称呼不同被建成多条（≤2 次误建/50 条） |
| **提醒** | 到期未联系的人推出来 | 48 小时关机后重开，只提醒一次（状态机保证） |
| **搜索** | 对姓名/公司/备注/记录做全文搜索（SQLite FTS5） | 1 万条记录下 P95 < 50ms |
| **导出** | JSON（权威）、vCard（仅基础字段）、复制到剪贴板 | JSON 往返恢复无损 |
| **Key 管理** | `keyring` 存系统钥匙串；支持「每次输入」模式 | 磁盘上不出现明文 key |

### 3.2 v1 不做（明确列出，避免蔓延）

- ❌ 多人共享 / 团队空间 / 权限体系
- ❌ 手机端、云同步、跨设备合并
- ❌ 自动抓取（通讯录、邮件、微信、日历）
- ❌ 群发消息 / 模板群聊
- ❌ 日历双向同步（v1 只做"到期清单"，不写回日历）
- ❌ 数据统计看板、图表
- ❌ 账号体系、支付、埋点、遥测
- ❌ vCard **导入**（只导出；导入只支持 JSON）

### 3.3 两处「30 分钟实现」的修正（C7）

| 原计划 | 实际情况 | v1 决定 |
|---|---|---|
| vCard 导出「30 分钟」 | vCard 只能承载姓名单值字段；`reminder` / `cadence` / 交互历史全丢 | 定位为「**给别人的兼容导出**」，30~60 分钟可做完，但不是备份手段 |
| 系统分享菜单「30 分钟」 | Windows 没有统一的"分享"入口，跨平台需分别适配 | v1 只做「导出到文件 + 复制到剪贴板」，分享菜单延后 |

## 4. 核心流程

### 4.1 记人（主路径，目标 P50 ≤ 3s）

```
[全局热键 Ctrl+Alt+R]
      │  ≤0.5s
      ▼
[输入框]  ← 一句话原文
      │  回车
      ▼
[抽取]  规则抽取（本地，<50ms）→ 若开启 LLM：结构化抽取（1~3s，失败降级）
      │
      ▼
[确认表单]  预填：姓名 / 公司 / 职位 / 发生时间 / 承诺 / 下次联系
      │      + 消歧候选：「是这位吗？[张三·XX公司] [新建]」
      │  用户改 1~2 个字段 → 点「确认」
      ▼
[capture.status = confirmed] → 写 interaction → 更新 person.last_contact_at / next_due_at
```

**关键设计：`capture` 与 `interaction` 分离**。原始一句话永不改写（可回溯、可重跑抽取），
`interaction` 只在用户确认后产生（P2 的物理保证）。

### 4.2 打开时的逾期提醒

```
[启动 / 每分钟 tick]
      ▼
查询 reminder: state='pending' AND due_at <= now
      ▼
按 person 聚合 → 一条通知（避免开屏弹 20 个气泡）
      ▼
每个 reminder 立即 state='notified', notified_at=now（幂等：重复 tick 不再弹）
      ▼
用户操作：完成 / 延后 3 天 / 静音此人 → 更新状态
```

### 4.3 导出

```
[导出 JSON]  person + alias + interaction + reminder（capture 可选包含原始文本）
[导出 vCard] 仅 name / org / title / note → 明确告知「不含提醒与历史」
[复制到剪贴板] 当前人的摘要文本（用于粘贴到聊天窗口）
```

## 5. 系统架构

### 5.1 分层（依赖只能向下，禁止反向）

```
┌─────────────────────────────────────────────┐
│  interfaces   CLI / GUI / 托盘 / 全局热键      │  可替换外壳
├─────────────────────────────────────────────┤
│  app          用例编排（record / remind / export）│  只依赖 domain + ports
├─────────────────────────────────────────────┤
│  domain       实体、抽取、消歧、调度规则        │  纯函数，零 IO
├─────────────────────────────────────────────┤
│  ports        抽象：Clock / LlmClient / Notifier / Repo │  协议定义
├─────────────────────────────────────────────┤
│  infra        sqlite / httpx / keyring / 托盘实现 │  端口的具体实现
└─────────────────────────────────────────────┘
```

**唯一例外**：`interfaces` 可以依赖 `infra` 做装配（composition root），但 `domain` 永远不 import 任何 IO。

### 5.2 三个必须存在的缝（seam）

| 端口 | 为什么必须有 | 测试里怎么用 |
|---|---|---|
| `Clock` | 提醒 / 逾期 / 日期解析全依赖"现在几点" | `FakeClock` 直接跳到 3 天后，测补发与幂等 |
| `LlmClient` | 抽取质量与失败路径必须可重现 | `FakeLlm` 返回预设 JSON / 超时 / 非法 schema |
| `Notifier` | 通知无法在 CI 里断言 | `RecordingNotifier` 记录调用次数与内容 |

> 这条规则的作用：**没有缝，就没法写出"48 小时后只提醒一次"这种测试**，而这个测试恰恰是你最有说服力的证据。

### 5.3 线程模型（v1 刻意保守）

- 主线程：UI 事件循环；
- 单后台线程：调度 tick（60s）+ 一次只跑一个提醒批次；
- 抽取：同步调用 LLM，UI 显示"正在识别…"并允许取消（超时 10s）。

> **v1 不引入线程池与任务队列**。理由：单人使用、并发度 1，引入并发只会增加 bug 面积。
> 这一点要写进 README 的"设计决策"，因为它体现了**按规模选复杂度**的判断力。

## 6. 里程碑（4 周 + 1 周缓冲）

| 里程碑 | 周期 | 交付 | 验收（不达标就不进下一个） |
|---|---|---|---|
| **M1 领域闭环** | 第 1 周 | `sqlite` 数据层 + 规则抽取 + CLI：`remember` → 预填 → 确认 → 入库 → `export json` | 全离线可跑；≥20 条单测绿；JSON 往返无损 |
| **M2 LLM 与消歧** | 第 2 周 | LLM 抽取（schema + 修复重试 + 降级）、调用日志、消歧候选、50 条评测脚本 | 输出字段级准确率；断网自动降级；重复提交不产生重复 interaction |
| **M3 界面与搜索** | 第 3 周 | GUI 外壳（热键 + 确认表单 + 列表）、FTS5 搜索 | 热键→确认 P50 ≤ 3s（实测记录）；1 万条 P95 < 50ms |
| **M4 提醒与发布** | 第 4 周 | 提醒状态机 + 补发 + 托盘通知 + vCard + 打包 + README/GIF | 关机 48h 后只提醒一次；打包产物双击可运行 |
| **M5 缓冲** | 第 5 周 | 修 bug、补文档、录演示、写 ADR | 移植到另一台机器能跑（无隐形依赖） |

**M1 刻意不写 GUI**：这样即使界面卡住，项目仍是一个可演示、可测试的完整工具。

## 7. 测试策略（摘要）

| 层 | 数量目标 | 依赖 | 说明 |
|---|---|---|---|
| domain 单测 | **最多**（≥60%） | 无 | 抽取规则、日期解析、消歧打分、下次联系时间计算、状态机迁移 |
| app 集成 | 中 | 内存 / 临时 sqlite | `record`、`confirm`、`remind_tick`、`export/import` 往返 |
| infra | 少量 | 真实 sqlite | 迁移、唯一约束、FTS5 查询 |
| interface | 最少 | subprocess | CLI 退出码、`--offline` 行为 |

**硬性要求**：覆盖率 ≥80%（`domain` ≥90%），且以下 6 条用例必须存在：

1. 未确认的 `capture` 不产生 `interaction`；
2. 同一 `capture` 重复确认 → 只有一条 `interaction`；
3. `FakeClock` 前进 48h → 提醒恰好触发一次；
4. LLM 返回非法 JSON → 修复重试 1 次 → 再失败降级为规则抽取；
5. 别名「张总」→ 消歧命中已知 person，不新建；
6. `export → 清空 → import` 后逐字段相等。

## 10. 架构决策记录（ADR）

| 编号 | 决策 | 理由 | 放弃了什么 |
|---|---|---|---|
| ADR-001 | **SQLite 单文件**，不存 JSON 文件 | 事务、唯一约束（幂等）、FTS5 全文搜索、单文件备份 | 手改数据的便利性（用导出解决） |
| ADR-002 | **Pydantic v2** 做领域模型与 LLM 输出校验 | 结构化输出必须有严格 schema；错误信息可直接回灌给模型修复 | 零依赖（多一个包） |
| ADR-003 | **httpx 直连 OpenAI 兼容接口**，不用各家 SDK | 一套代码可接 DeepSeek / 通义 / Ollama / OpenAI；SDK 会锁生态 | SDK 的便利封装 |
| ADR-004 | **规则抽取为默认，LLM 为增强** | 离线可用、可测、可降级；LLM 只负责"更好"不负责"能不能用" | "全 AI" 的产品观感 |
| ADR-005 | **提醒用状态机 + 启动补发**，不用系统计划任务 | 可测、跨平台、无平台权限申请 | 关程序时的实时提醒 |
| ADR-006 | **v1 不引入线程池/队列/服务端** | 并发度 1，按规模选复杂度 | 未来扩展性（v2 再说） |
| ADR-007 | **PySide6-Essentials**（2026-10-21 已定） | 托盘 / 全局热键 / 通知有原生能力；实测 `cp310-abi3` wheel 可在 Python 3.14 安装；只用 Essentials，避免 Addons/WebEngine 多出数百 MB | 零依赖（Tkinter 方案，仅作降级） |

> ADR 的写法原则：每条都要写"我放弃了什么"。**只写优点的决策不算决策，算宣传。**

## 11. 面试叙事要点（这个项目能讲什么）

按"能被追问三层"的标准排序：

1. **HITL 设计**：为什么"预填+确认"优于"全自动"？→ 准确率 75% 下的期望损失计算；
2. **实体消歧**：为什么不交给 LLM？→ 确定性可测 vs 不可复现；候选打分公式与阈值取舍；
3. **提醒幂等**：关机 48 小时怎么办？→ 状态机 + 补发 + 唯一约束；
4. **LLM 工程化**：schema 校验、修复重试、降级、成本与延迟审计、评测集；
5. **隐私可验证**：怎么证明没有偷偷上传？→ 单一出口 + socket 拦截测试 + 调用日志；
6. **按规模选复杂度**：为什么不做服务端 / 不做队列？→ 并发度 1，复杂度要有收益。

**不要讲**："我用 Pydantic 校验 JSON"（这是工具用法，不是决策）。
