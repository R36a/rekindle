## 1. 数据模型

### 1.1 表结构（SQLite，迁移脚本放 `src/rekindle/infra/migrations/`）

```sql
PRAGMA journal_mode = WAL;          -- 允许"一个写多个读"
PRAGMA foreign_keys = ON;

CREATE TABLE person (
    id            INTEGER PRIMARY KEY,
    display_name  TEXT    NOT NULL,
    pinyin        TEXT    NOT NULL DEFAULT '',   -- 全拼，用于消歧
    initials      TEXT    NOT NULL DEFAULT '',   -- 首字母，用于消歧
    company       TEXT,
    role          TEXT,
    notes         TEXT,
    cadence_days  INTEGER,                       -- NULL = 不提醒
    last_contact_at TEXT,                        -- ISO8601（UTC）
    next_due_at     TEXT,                        -- 冗余字段，由 last_contact_at + cadence 派生
    archived      INTEGER NOT NULL DEFAULT 0     -- 归档而非删除（P0：不丢数据）
);

CREATE TABLE alias (
    id        INTEGER PRIMARY KEY,
    person_id INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
    text_norm TEXT    NOT NULL,                  -- 归一化后的称呼（去空格/统一大小写）
    source    TEXT    NOT NULL DEFAULT 'user'    -- user / extraction
);
CREATE UNIQUE INDEX ux_alias_person_text ON alias(person_id, text_norm);
CREATE INDEX ix_alias_text ON alias(text_norm);

CREATE TABLE capture (
    id             INTEGER PRIMARY KEY,
    raw_text       TEXT    NOT NULL,             -- 原始一句话，永不改写
    created_at     TEXT    NOT NULL,
    status         TEXT    NOT NULL,             -- draft / confirmed / discarded
    source         TEXT    NOT NULL,             -- rule / llm / manual
    parsed_json    TEXT,                         -- 抽取结果快照（可重跑对比）
    model          TEXT,
    prompt_ver     TEXT,
    llm_call_id    INTEGER,
    person_id      INTEGER REFERENCES person(id) -- 确认后回填
);

CREATE TABLE interaction (
    id           INTEGER PRIMARY KEY,
    person_id    INTEGER NOT NULL REFERENCES person(id),
    capture_id   INTEGER UNIQUE REFERENCES capture(id),  -- 幂等：一条记录只入库一次
    occurred_at  TEXT    NOT NULL,
    summary      TEXT    NOT NULL,
    promise      TEXT,                            -- "答应帮看简历"
    created_at   TEXT    NOT NULL
);
CREATE INDEX ix_interaction_person_time ON interaction(person_id, occurred_at DESC);

CREATE TABLE reminder (
    id          INTEGER PRIMARY KEY,
    person_id   INTEGER NOT NULL REFERENCES person(id),
    due_at      TEXT    NOT NULL,
    reason      TEXT    NOT NULL,                 -- 到期 / 用户手动
    state       TEXT    NOT NULL,                 -- pending / notified / done / snoozed / muted
    notified_at TEXT,
    snooze_until TEXT,
    created_at  TEXT    NOT NULL
);
CREATE INDEX ix_reminder_due ON reminder(state, due_at);

CREATE TABLE llm_call (
    id            INTEGER PRIMARY KEY,
    provider      TEXT NOT NULL,
    base_url      TEXT NOT NULL,                  -- 审计：到底发给了谁
    model         TEXT NOT NULL,
    prompt_ver    TEXT NOT NULL,
    prompt_hash   TEXT NOT NULL,
    request_json  TEXT NOT NULL,                  -- 全量原始请求（脱敏策略见 5.3）
    response_json TEXT,
    tokens_in     INTEGER,
    tokens_out    INTEGER,
    latency_ms    INTEGER,
    ok            INTEGER NOT NULL,
    error         TEXT,
    created_at    TEXT NOT NULL
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- schema_version 等
```

### 1.2 不变量（写进代码与测试，不靠自觉）

| # | 不变量 | 强制手段 | 对应测试 |
|---|---|---|---|
| I1 | `capture.status != 'confirmed'` 时**不得存在**对应 `interaction` | `record` 用例只在确认后写 interaction | 必测 1 |
| I2 | 一个 `capture` 最多一条 `interaction` | `interaction.capture_id UNIQUE` | 必测 2 |
| I3 | `reminder` 从 `pending` 只能到 `notified`/`muted`，`notified` 不再回到 `pending` | 状态迁移函数（唯一入口） | 必测 3 |
| I4 | 同一 `(person_id, text_norm)` 只有一条 `alias` | 唯一索引 | 消歧单测 |
| I5 | `next_due_at = last_contact_at + cadence_days`，`cadence_days IS NULL` 时为 NULL | 单一派生函数 `compute_next_due()` | 派生单测 |
| I6 | 删除一律用 `archived=1`（person）/ `discarded`（capture），**物理删除仅由"清理"命令触发** | 仓储层不暴露 delete | 数据安全测试 |

> 为什么把不变量单列：**它们是这个项目里唯一"不能被 UI 绕过"的东西**。UI 可以写错，数据库约束不能。

## 2. 抽取管线

### 2.1 总体流程

```
raw_text
   │
   ├─[A] 规则抽取（永远执行，<50ms，零网络）
   │      → ExtractionCandidate(confidence, evidence)
   │
   ├─[B] 若 LLM 启用：结构化抽取（超时 10s）
   │      成功 → ExtractionCandidate(confidence=high)
   │      失败 → 记录 llm_call(ok=0)，用 [A] 的结果
   │
   ├─[C] 合并：字段级取更高置信度（不是整条覆盖）
   │
   ├─[D] 校验（Pydantic）：字段类型/范围/时间格式
   │      失败 → 修复重试 1 次（把错误信息回灌给模型）
   │      仍失败 → 降级 [A]，并在 UI 标注「本次为离线识别」
   │
   └─[E] 生成确认表单（含消歧候选，见 3）
```

### 2.2 规则抽取要抽什么（M1 全部离线）

| 字段 | 规则 | 示例 |
|---|---|---|
| `display_name` | 中文姓名模式（2~4 字，姓氏表 + 上下文「和/跟/与 X」「X 老师/总/工」） | 「和张三在…」→ 张三 |
| `company` | 「在 X 工作/入职/实习」/「X 公司的」 | 「他在字节做后端」 |
| `role` | 职位词典（后端/前端/算法/产品/HR…） | 「做后端」→ 后端 |
| `occurred_at` | 今天/昨天/前天/上周X/上个月/X月X日/周X；无法解析 → 默认为 `created_at` | 「上周和张三…」→ 上周同日 |
| `promise` | 「答应/说好/承诺/回头 + 动词」片段 | 「答应帮看简历」 |
| `cadence_hint` | 「保持联系/隔段时间/每月」→ 30 天；无 → NULL | 「以后常联系」→ 30 |

**规则命中的每一条都要写 `evidence`（命中的子串与偏移）**，用于：
1. UI 上高亮"我为什么这么填"；
2. 评测时区分"规则抽错"还是"LLM 抽错"。

### 2.3 LLM 抽取的请求契约

```jsonc
{
  "model": "deepseek-chat",
  "temperature": 0,
  "response_format": { "type": "json_object" },
  "messages": [
    { "role": "system", "content": "<prompt v1：字段定义 + 禁止编造 + schema>" },
    { "role": "user",   "content": "<raw_text>" }
  ]
}
```

Pydantic 侧（严格模式）：

```python
class ExtractedFields(BaseModel):
    model_config = ConfigDict(extra="forbid")

    display_name: str = Field(min_length=1, max_length=20)
    company: str | None = None
    role: str | None = None
    occurred_at: date | None = None          # 只给日期，时间由系统补
    promise: str | None = None
    cadence_days: int | None = Field(default=None, ge=1, le=365)
    confidence: float = Field(ge=0, le=1)
```

三条硬规则：

1. **`extra="forbid"`**：多返回字段视为失败 → 防止模型"自由发挥"污染数据；
2. **`temperature=0`**：可复现优先；
3. **`prompt_ver` 入库**：换 prompt 后可对比同一批输入的效果差异（这是评测的基础）。

### 2.4 失败矩阵（每种失败都有确定行为，不留"看情况"）

| 失败 | 行为 | 用户看到 |
|---|---|---|
| 网络不通 / 超时 | 记录 `llm_call.ok=0`，用规则结果 | 「离线识别」标签 |
| 返回非 JSON | 修复重试 1 次（附错误） | 重试失败 → 离线标签 |
| JSON 合法但 schema 不合 | 同上（附 Pydantic 错误路径） | 同上 |
| 缺少 `display_name` | 直接判为失败（姓名是唯一必需字段） | 表单留空，光标停在姓名框 |
| 429 / 5xx | 指数退避重试 2 次（0.5s、1.5s），仍失败则降级 | 离线标签 + 可点"重试" |

### 2.5 成本与延迟

- 每次调用记录 `tokens_in / tokens_out / latency_ms`，UI 显示最近一次耗时；
- README 给出「一句话记录 ≈ 多少 token ≈ 多少钱」的**实测值**（用自己 20 条真实输入统计，不估算）；

## 3. 实体消歧（这个项目技术含量最高的部分）

### 3.1 目标与原则

- **宁可多建，不可错并**（错误合并会导致两条真实关系被搅在一起，且很难发现）；
- 只用**确定性可测**的规则打分，不把"是不是同一个人"交给 LLM；
- 用户确认后把称呼写入 `alias`，实现"越用越准"。

### 3.2 候选生成（先粗筛，再打分）

```
给定抽取到的 display_name（归一化：去空格、去"老师/总/工"后缀、全角转半角）
  ① alias 精确匹配          → 直接高置信候选
  ② 姓名精确匹配
  ③ 拼音全拼相同（同音字，如"张伟"/"张玮"）
  ④ 姓名首字母相同且 company 相同
  ⑤ 编辑距离 ≤ 1（仅对 ≥3 字的姓名启用）
  ⑥ 无候选 → "新建"
```

### 3.3 打分公式（每一项都可单测）

```
score = 5 * exact_alias
      + 4 * exact_name
      + 3 * same_pinyin_full
      + 2 * (same_initials and same_company)
      + 1 * (edit_distance == 1)
      + 2 * same_company
      + 1 * role_similar
      - 3 * (company_conflict)          # 两边都有公司且不同 → 强负分
```

| 区间 | 行为 |
|---|---|
| `score >= 7` | 默认选中该候选（**仍需用户点确认**，违反 P2 的全自动一律不允许） |
| `3 <= score < 7` | 展示候选，默认选"新建"，用户可改 |
| `score < 3` | 只展示"新建" |

> 阈值不许凭感觉定：用自己 50 条真实记录做标注，画出"误并 vs 漏并"曲线后选点，
> 并把这段分析写进 README（这是面试里最容易被记住的一段）。

### 3.4 别名学习

- 用户选择"是这位"后，把本次称呼（归一化）写入 `alias(person_id, text_norm)`；
- `alias` 唯一索引保证不重复；
- 用户在选择时勾选"这是同一个人的另一种叫法（永久记住）"→ 才写 alias；
  否则只写本次 interaction（避免把一次口误变成永久映射）。

### 3.5 合并（手动，且可撤销）

- v1 **只提供手动合并**：选中两条 person → 合并 → 保留一条，另一条 `archived=1`，alias 与 interaction 全部迁移；
- 合并写一条 `meta` 记录（可回看"什么时候合并了谁"）；
- **不做自动合并**（风险 R4）。

## 4. 提醒调度

### 4.1 派生规则（单一函数，I5）

```python
def compute_next_due(last_contact_at: datetime | None, cadence_days: int | None) -> datetime | None:
    if cadence_days is None:
        return None
    base = last_contact_at or created_at
    return base + timedelta(days=cadence_days)
```

- `cadence_days` 三种来源：用户手填 > 抽取的 `cadence_hint` > 全局默认（可关闭）；
- 修改 `last_contact_at` 或 `cadence_days` 后**必须重算** `next_due_at`（在同一个事务里）。

### 4.2 状态机（唯一入口 `transition(reminder, action)`）

```
                 ┌───────────── snooze(n天) ─────────────┐
                 ▼                                       │
   [pending] ──tick 到点──> [notified] ──完成──> [done]   │
        │                        │                      │
        │                        └──静音此人──> [muted]  │
        └── 用户手动延后 ──> [snoozed] ──到点──> [pending]─┘
```

| 迁移 | 允许？ | 副作用 |
|---|---|---|
| `pending → notified` | ✅ | 写 `notified_at`（**幂等的关键**） |
| `notified → pending` | ❌ | 禁止（否则会重复弹） |
| `pending/notified → done` | ✅ | 关闭该提醒 |
| `pending → snoozed` | ✅ | 写 `snooze_until`，到期由 tick 转回 `pending` |
| 任意 → `muted` | ✅ | 静音该人的所有提醒 |

### 4.3 去重与补发（对应必测 3）

```python
def tick(now: datetime) -> list[Notification]:
    # 1) 原子地把"到点且 pending"的提醒改成 notified，返回被改的那些
    rows = repo.claim_due_reminders(now)        # UPDATE ... WHERE state='pending' AND due_at<=now RETURNING *
    # 2) 按 person 聚合，一人一条
    return group_by_person(rows)                # 例：3 个逾期 → 1 条"你有 3 位需要联系"
```

- `claim_due_reminders` 用**一条 UPDATE ... RETURNING** 完成"查+改"，天然防重复；
- 启动时立刻执行一次 `tick(now)` → **关机 48 小时后重开，逾期提醒一次性补发，且只发一次**；
- 通知里显示"最早逾期 X 天"，并按逾期天数排序。

### 4.4 平台触发（不依赖服务端）

| 平台 | 方案 | 备注 |
|---|---|---|
| Windows | 托盘常驻进程 + 开机自启（注册表 `Run`） | v1 主目标平台 |
| macOS / Linux | 托盘 + `launchd` / `systemd --user`（延后） | v1 不保证 |

## 5. 隐私与可验证性

### 5.1 对外声明（README 原文，必须与实现一致）

> **无自有服务端**：项目不运营任何服务器，不收集任何遥测。
> **两种运行模式**：
> - 离线模式（默认）：不产生任何网络请求；
> - LLM 模式：**你输入的原文**会发送到**你自己配置的端点**（域名在设置里可见）。
> 每次调用都记录在本地 `llm_call` 表，可查看、可导出、可删除。

### 5.2 可验证性（原则"不接受相信"的落地）

| 主张 | 验证方式（用户可自己做） |
|---|---|
| 离线模式零联网 | 命令 `rekindle --offline verify`：用 socket 钩子跑一遍主流程，打印"出站连接数 = 0" |
| 只连配置的域名 | 设置页显示当前 `base_url`；`rekindle audit connections` 列出历史上出现过的所有域名（来自 `llm_call.base_url` 去重） |
| 发送了什么内容 | 确认表单下方可展开"将要发送的文本（原文）"；`llm_call.request_json` 可查 |
| 数据可带走 | `rekindle export --format json` → 单文件；`rekindle import` 到空库逐字段一致 |
| 可彻底删除 | `rekindle purge --person 3` / `--all`（物理删除，含 llm_call 相关记录），执行前二次确认 |

### 5.3 脱敏策略（避免"审计日志本身成为隐私风险"）

- `llm_call.request_json` **默认存原文**（否则无法回放），但提供 `--redact-log` 选项：只存 `prompt_hash` 与字段名；
- 日志文件权限：Windows 下尽力设置 ACL（`icacls`），失败时在 README 说明"未加密，请自行保护用户目录"——**不吹做不到的事**；
- 不记录 API key（key 只在 `keyring`；日志里出现 key 视为 P0 bug）。

### 5.4 测试里的强制断言

```python
def test_offline_mode_makes_no_connection(monkeypatch_fake_socket):
    run_record_pipeline(offline=True)
    assert monkeypatch_fake_socket.connect_calls == []
```

> 这条测试是"隐私承诺"的唯一硬证据。没有它，README 里那句话就是营销。

## 6. 评测方案（把"75% 准确率"变成可复现的数字）

### 6.1 数据集

- 位置：`eval/dataset.jsonl`（**已脱敏**，用化名替换真实人名/公司）；
- 规模：**50 条** v1 起步；每条含 `raw_text` + 人工标注的 `expected`（只标 6 个字段）；
- 来源：优先用自己真实输入（脱敏后），不足部分用改写生成；
- 版本：数据集更新要在 README 记录（`dataset v1 → v2`），保证历史数字可比。

### 6.2 指标口径（必须写死，否则数字没有意义）

| 字段 | 判定为"对"的条件 |
|---|---|
| `display_name` | 归一化后**完全相等** |
| `company` / `role` | 归一化后相等，或一方为空且另一方为空 |
| `occurred_at` | 日期完全相等（时分不计） |
| `promise` | 关键词集合的 Jaccard ≥ 0.5（不要求逐字） |
| `cadence_days` | 完全相等，或均为 NULL |

整体准确率 = **字段级正确数 / 字段总数**（不是"整条全对才算对"，否则数字会被最难字段拖死，也不能反映实际体验）。

### 6.3 输出

```
rekindle eval --dataset eval/dataset.jsonl [--offline] [--model ...]
→ 控制台：字段级准确率表 + 95% 置信区间（n=50 时区间很宽，要如实标出）
→ eval/reports/2026-10-21-llm-v1.json：逐条明细（哪条错、错在哪个字段）
```

**必须诚实的两点**：
1. n=50 的置信区间大约 ±12%，README 里要写"样本量小，仅供参考"；
2. 报"字段级准确率"而不是"准确率"，因为后者定义模糊。

### 6.4 调优闭环

```
改 prompt / 改规则 → 跑 eval → 对比 reports → 只接受"整体提升且无字段退化"的改动
```
—— 这个闭环本身就是面试可讲的工程实践（**回归测试保护 prompt**）。

## 7. 测试策略（可执行版）

### 7.1 目录与职责

```
tests/
  unit/        domain 纯函数：日期解析、姓名正则、打分公式、compute_next_due、状态迁移
  integration/ app 用例 + 临时 sqlite：record / confirm / tick / export-import
  interface/   CLI：--version、--offline、退出码
  fixtures/    FakeClock / FakeLlm / RecordingNotifier / 已脱敏样本
```

### 7.2 六条必测（对应开发文档第 7 节）

| # | 用例 | 断言要点 |
|---|---|---|
| 1 | 未确认不产生 interaction | `confirm` 前后 `interaction` 行数不变 |
| 2 | 重复确认只入库一次 | 第二次 `confirm` 抛 `AlreadyConfirmed` 或幂等返回，行数仍为 1 |
| 3 | 48h 后只提醒一次 | `FakeClock` 前进 48h → `tick()` 返回 1 条；再 `tick()` 返回 0 条 |
| 4 | 非法 schema → 重试 → 降级 | `FakeLlm` 前两次返回坏 JSON → 结果 `source == "rule"` 且 `llm_call` 有 2 条 `ok=0` |
| 5 | 别名命中不新建 person | 「张总」→ 命中已存 alias，`person` 行数不变 |
| 6 | 导出导入往返一致 | 逐表逐字段比较（忽略自增 id，用业务主键比对） |

### 7.3 时间与网络的隔离规则（代码级约束）

- 生产代码中**禁止直接调用** `datetime.now()` / `time.time()`（用 `Clock`）；
- 生产代码中**禁止直接** `import httpx`（只有 `infra/llm_http.py` 可以）；
- CI 里加两条 grep 断言（`ruff` 规则或简单脚本），违反即失败。

> 这两条约束是"可测试性"的物理保障，比喊口号有效。

### 7.4 覆盖率与 CI

- `pytest --cov=src/rekindle --cov-fail-under=80`；
- `domain/` 单独要求 `--cov-fail-under=90`；
- CI 顺序：`ruff check` → `mypy --strict` → `pytest` → `pytest --cov`；
- **不准提交 `# type: ignore` / `# noqa` 而不写理由**（CI 用注释检查脚本兜底）。

## 9. 字段自定义设计（T2，对 §1/§2 的 v0.3 修订）

### 9.1 约束（2026-10-21 用户原话）

> 字段添加除了初始的几个，不可以让 AI 添加或者删除，AI 只可以给人脉中的人添加当前字段。

落地为三条硬规则：
1. **字段集由用户管理**：只有用户能新增 / 删除字段。
2. **AI 不增删字段**：只能往「当前已存在的字段」填值。
3. **AI 只填值**：输出里出现注册表没有的字段名 → 视为错误（等价 extra="forbid"）。

### 9.2 字段分两类

| 类别 | 存储 | 例子 | 谁管 |
|---|---|---|---|
| 系统字段（结构） | person 固定列 | display_name / cadence_days / last_contact_at / next_due_at / notes / archived | 系统，不可删，驱动消歧/提醒/排序 |
| 属性字段 | person_field 键值 | 公司 / 职位 / 承诺 / 生日 / 爱好…… | 用户增删，AI 只填 |

为什么这么分：系统字段要高频查询、参与排序和提醒计算，需要类型安全 + 索引；属性字段是记录性质、数量不定，放键值表最灵活。

### 9.3 字段注册表 field

> **实现状态（2026-10-25，schema v7）**：当前实现**没有** field 表——字段集合的唯一来源是
> `domain/fields.py` 的 `DEFAULT_FIELDS`（派生 `FIELD_KEYS`）。原表只有四行种子，且
> label / field_type / description / builtin 没有任何读者，等于同一事实存两份；结果是
> 「UI 认常量、仓储认表」，编辑保存时会把表里有、UI 不认识的字段静默删掉，所以 v7 删表
> （v6→v7 迁移保留 person_field 的值）。本节的注册表设计留待「用户自定义字段」真正开工时
> 再落地，届时必须同时提供字段增删入口 + 动态表单，否则会重演上述丢值问题。

```sql
CREATE TABLE field (
    key         TEXT PRIMARY KEY,
    label       TEXT NOT NULL,
    type        TEXT NOT NULL,            -- text / date / number
    description TEXT NOT NULL DEFAULT '',  -- 给 AI 的抽取说明
    builtin     INTEGER NOT NULL DEFAULT 0, -- 1=初始字段
    protected   INTEGER NOT NULL DEFAULT 0  -- 1=不可删
);
```

初始字段（builtin=1，种子）：company（公司）、role（职位）、promise（承诺）、birthday（生日，示例）。
`name` / `occurred_at` / `cadence` / `notes` 是系统字段，不进注册表。

### 9.4 属性值表 person_field

```sql
CREATE TABLE person_field (
    person_id INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
    field_key TEXT    NOT NULL REFERENCES field(key) ON DELETE CASCADE,
    value     TEXT    NOT NULL,           -- 统一存文本，date/number 由 field.type 约束
    PRIMARY KEY (person_id, field_key)
);
```

不变量：同一人对同一字段只有一个值（复合主键）；`field_key` 必须存在于 field（外键），删字段级联清空对应值；AI 产出里出现未注册的 key → 校验失败。

### 9.5 抽取 schema 由注册表动态生成

LLM 只填注册表里的字段；字段的增删入口只在「字段管理」，AI 与抽取管线没有该能力。

### 9.6 动态表单

表单 = 系统字段（固定在上方）+ 注册表字段（动态渲染、AI 预填）。用户增删字段后，下次记录时表单自动变化，无需改代码。

### 9.7 对现有代码的影响

- Person 移除 company / role 固定列，改读 person_field；
- ExtractedFields 改为 system + attributes（attributes 的 key 受注册表校验）；
- 规则抽取（T3）只抽系统字段 + builtin 属性字段，自定义字段交给 LLM。

### 9.8 待定

- promise 归 person_field 还是保留在 interaction？倾向保留 interaction.promise（与「一次见面」绑定）。
- 属性值统一存 TEXT，type 只做展示/校验，暂不做原生 date/number 列。

## 10. 待办（Todo）设计 —— 取代原「承诺 promise」（2026-10-21）

### 10.1 定位

- 待办是**一等实体**（独立表），不是 person_field 里的值，也不是 interaction.promise。
- 与「提醒」的区别：reminder = 按联系频率派生的「该联系这个人了」；todo = 用户/AI 明确记录的「具体要做什么」（可多人、可重复）。

### 10.2 表结构

```sql
CREATE TABLE todo (
    id          INTEGER PRIMARY KEY,
    title       TEXT NOT NULL,
    notes       TEXT NOT NULL DEFAULT '',
    next_due_at TEXT,                        -- 下一次时间；NULL = 不提醒
    repeat_rule TEXT NOT NULL DEFAULT 'none', -- none(不重复) / daily(每天) / weekly(每周) / monthly(每月) / yearly(每年) / custom(自定义)
    repeat_days INTEGER,                     -- repeat_rule=custom 时的间隔天数
    status      TEXT NOT NULL DEFAULT 'open', -- open / done / archived
    created_at  TEXT NOT NULL,
    completed_at TEXT
);

CREATE TABLE todo_person (
    todo_id   INTEGER NOT NULL REFERENCES todo(id) ON DELETE CASCADE,
    person_id INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
    PRIMARY KEY (todo_id, person_id)
);
```

### 10.3 规则

1. 一个待办可关联 0..n 个人，一个人可关联多个待办（多对多，todo_person）。
2. 重复：不重复(none) 完成后 status=done 不再提醒；daily/weekly/monthly/yearly/custom 完成时 next_due_at 顺延、status 回 open。顺延用单一函数 advance_due(todo, now)，可测。
3. 待办到期与「联系人提醒」一起进通知（M4 统一）。

### 10.4 抽取影响

- 一句话 → 可能抽出「待办列表」，每项含：标题、时间、涉及的人（可能多个）、是否重复。
- 规则版（T3）先只做「答应/说好/承诺 + 时间」→ 单条待办、单人；多人、重复交给 LLM（T4）。

### 10.5 取代

- 本节取代 §9.8 里「promise 归 person_field 还是 interaction」的待定项：promise 概念移除，统一改为待办实体。
- ExtractedFields 里的 promise 字段移除，改为 todos: list[TodoDraft]。

## 11. 权限设置与存档（2026-10-21 新增）

### 11.1 AI 权限设置（默认最小权限）

把 §9.1 写死的约束改为「用户设置」，默认全部关闭：

| 设置项 | 默认 | 含义 |
|---|---|---|
| ai_add_field | false | 允许 AI 新增字段 |
| ai_delete_field | false | 允许 AI 删除字段 |
| ai_auto_commit | false | 允许 AI 不经确认直接入库 |
| ai_snapshot | false | 允许 AI 触发存档 |

不变量：
- 开关关闭时，对应能力在代码层直接不提供（不只是 UI 藏起来）；
- 用户随时可改、可收回，改动立即生效。

### 11.2 存档（类似 git）

把数据做成「可回滚的快照」，像 git 一样能提交、看历史、回退。

- 手动存档：带一句备注，生成一个快照点；
- 自动存档：按设置触发；
- 历史：列出所有快照（时间 + 备注 + 数据规模），可查看、可回滚到任意点；
- 回滚：恢复数据到某个快照，回滚前自动再存一个「回滚前」快照，防手滑。

### 11.3 存档相关设置

| 设置项 | 默认 | 含义 |
|---|---|---|
| auto_snapshot | true | 自动存档开关 |
| auto_snapshot_frequency | 每次退出 | 每次启动 / 每天 / 每次退出 |
| snapshot_keep | 30 | 保留最近 N 个快照 |
| snapshot_dir | user_data/snapshots | 快照目录 |

### 11.4 实现取舍（实现时再定）

- 先用「简单文件快照」（复制 .db + index 记录备注），不真接 git；理由：二进制 .db 的 diff 意义不大，快照已够用且少一个依赖。
- 后续若想要「字段级 diff / 谁改了什么」，再把数据落成可 diff 的 JSON 再 git。
